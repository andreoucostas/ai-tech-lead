## 7. Querying this warehouse

Rules for reading this warehouse, not loading it. They address the ways a report goes wrong
quietly — producing a number, not an error.

1. **Start at `fact.FactSales` and state its grain** in one sentence before writing any SQL: one
   row per source sales order (`SalesKey = stg.StgSalesOrder.SalesId`).
2. **Reach an attribute by following a fact key to the dimension that owns it.** Never read it off
   a column that merely happens to sit on a table already in the join. `fact.FactSales.RegionName`/
   `CategoryName`/`SegmentName` are declared in DDL but never populated by `usp_LoadFactSales` — a
   `SELECT` against them returns `NULL`, not an error (Finding F8). Always join to
   `dim.DimRegion`/`dim.DimProduct`/`dim.DimCustomer` for these values instead, the way
   `rpt.vwExecutiveSummary` and `rpt.vwFinanceExtract` already do.
3. **Use an existing reporting view's join path as a usage lead before inventing one.**
   `rpt.vwFinanceExtract`'s `FactSales → DimCustomer → DimRegion` path is the only evidenced way to
   reach region from the fact — but see rule 6 below: it currently always returns `'Unknown'`
   (Finding F3), which is a data problem in the load, not a join-path problem.
4. **Treat a same-named column on an already-joined table as suspect** until you know which table
   populates it. Same name is not same meaning, and it is not evidence of a relationship —
   `fact.FactSales.LoadRunId` looks like a `ctl.LoadRun` reference by name but is actually sourced
   from `stg.StgSalesOrder.BatchId` (Finding F5).
5. **Replicating a report from another warehouse: write the source-column → target-concept mapping
   before any SQL.** Same-named columns across two warehouses are the trap this rule exists for.
   Name what is unresolved and ask — do not substitute the nearest-looking column.
6. **Add an effective-date predicate only when the key does not already identify one version.** The
   discriminator is a property of the edge, and the edge list in section 2 records it as
   `version resolution`:
   - **`Pinned at load`** — `fact.FactSales.CustomerKey` (and `ProductKey`, `OrderDateKey`) were
     stamped at load time from the dimension row that was current then. Adding
     `EffectiveFrom`/`EffectiveTo`/`IsCurrent` to a join on these keys would silently drop rows
     pointing at a superseded version. In practice `dim.DimCustomer` never actually produces a
     second version today (Finding F2), so this risk is latent rather than active — but it becomes
     real the moment F2 is fixed and Type-2 versioning starts working as designed.
   - **`Deferred to query`** — no edge in this warehouse is currently `Deferred to query`.
   - **UNRESOLVED** — none of the four edges in section 2 are UNRESOLVED; if a new edge is added
     that is, do not guess — copy an existing view's join or ask.

Two named path hazards:

- **Fan trap** — joining a chained one-to-many below `fact.FactSales` multiplies fact rows and
  double-counts `NetAmount`. None of the current dimensions are one-to-many below the fact grain,
  so this isn't active today — but watch for it if a bridge table is ever added.
- **Chasm trap** — joining two facts directly through a shared dimension multiplies rows within
  each shared key group. Not yet applicable — this repo has only one fact (`fact.FactSales`).

If a future edge is marked `UNRESOLVED` or `CONFLICTING`, that is the map telling you it does not
know — treat it as a question to ask, not a gap to fill with the most plausible-looking column.
