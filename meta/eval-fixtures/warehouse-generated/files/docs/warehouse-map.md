## 4. Dimensional semantics

- **Fact type**: `fact.FactSales` is a **transaction fact** — one row per sales-order line/event.
- **Measure additivity**: `NetAmount` is **fully additive** (a currency amount per line, summable across every dimension) — no evidence of balance/snapshot semantics.
- **Role-playing dimensions**: none found — `fact.FactSales` has exactly one date key (`OrderDateKey`); no second date role (e.g. a ship date) exists.
- **Snowflaked (not role-playing) dimension**: `dim.DimRegion` is not reached directly from the fact at all — it is reached only by following `dim.DimCustomer.RegionKey`, one hop off the customer dimension. `Views/rpt.vwFinanceExtract.sql` is the only object in the repo that performs this hop.
- **Conformed dimensions**: `dim.DimCustomer`, `dim.DimProduct`, and `dim.DimDate` are each used by exactly one fact (`fact.FactSales`) — there is no second fact in this repository to test conformance against.
- **Degenerate dimension**: `fact.FactSales.SalesKey` (= `stg.StgSalesOrder.SalesId`) is an order-line identifier carried directly on the fact with no separate dimension table.
- **Misleading column naming**: `fact.FactSales.LoadRunId` is named after `ctl.LoadRun.LoadRunId` but is actually sourced from `stg.StgSalesOrder.BatchId`; `ctl.LoadRun` is never written or read anywhere in this repository. Treat any assumption that `LoadRunId` references `ctl.LoadRun` as false (Finding F5).

## 7. Querying this warehouse

Rules for reading this warehouse, not loading it. They address the ways a report goes wrong
quietly — producing a number, not an error.

1. **Start at `fact.FactSales` and state its grain** — one row per staged sales-order line — before writing any SQL. If you're building a new fact, resolve its grain first.
2. **Reach an attribute by following a fact key to the dimension that owns it.** Never read it off a column that merely happens to sit on a table already in the join. `fact.FactSales.RegionName`/`CategoryName`/`SegmentName` are declared in DDL but populated by nothing (Finding F8) — they look like real columns and return `NULL`, not an error. Reach region through `CustomerKey → dim.DimCustomer.RegionKey → dim.DimRegion`, not off the fact directly.
3. **Use `Views/rpt.vwFinanceExtract.sql` or `Views/rpt.vwExecutiveSummary.sql` as a usage lead for a join path, not proof it's correct.** They show the paths this warehouse actually uses. If you need the region breakdown, know going in that every row currently reads `'Unknown'` (Finding F3).
4. **Treat `fact.FactSales.LoadRunId` as suspect** — it is not a `ctl.LoadRun` reference despite the name (Finding F5); it is `stg.StgSalesOrder.BatchId`.
5. **Replicating a report from another warehouse**: write the source-column → target-concept mapping before any SQL. Same-named columns across two warehouses are the trap this rule exists for.
6. **Add an effective-date predicate only when the key does not already identify one version.** `dim.DimCustomer` is reached from `fact.FactSales.CustomerKey` as **Pinned at load** — the load already selected the current customer version and stamped that version's key onto the fact. Adding an `IsCurrent = 1` filter to that join again is redundant at best; if a future load changes this to a durable/natural key, the resolution becomes `Deferred to query` and the predicate becomes required. `dim.DimProduct` and `dim.DimDate` are Type 1 (one version per entity), so this question doesn't arise for them.

Two named path hazards:

- **Fan trap** — joining a chained one-to-many below `fact.FactSales` multiplies rows and double-counts `NetAmount`. None of the current views do this, but watch for it if `dim.DimProduct` or `dim.DimCustomer` ever gain a one-to-many child table.
- **Chasm trap** — joining two facts directly through a shared dimension multiplies rows within each shared key group. Not currently reachable (`fact.FactSales` is the only fact), but applies the moment a second fact is added that shares `dim.DimCustomer`, `dim.DimProduct`, or `dim.DimDate`.

If a future edge in section 2 is marked `UNRESOLVED` or `CONFLICTING`, that is the map telling you it does not know — treat it as a question to ask, not a gap to fill with the most plausible-looking column.
