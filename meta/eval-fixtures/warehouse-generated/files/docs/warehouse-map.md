## 4. Dimensional semantics

- **Fact type**: `fact.FactSales` is a **transaction fact** — one row per source sales order, inserted once by `usp_LoadFactSales` with no periodic-snapshot or accumulating-snapshot pattern evidenced.
- **Measure additivity**: `NetAmount` is treated as **fully additive** across all current dimensions (customer, product, date) — nothing in the schema or loads suggests a semi-additive balance/level semantic. No reversal, correction, or refund mechanism is evidenced (see Coverage), so additivity across time for corrected/late-arriving orders is untested.
- **Role-playing dimensions**: none currently — `dim.DimDate` is reached only via the single `OrderDateKey` role. If a `ShipDateKey` or similar is added later, re-run this map to record the additional role.
- **Conformed dimensions**: not applicable yet — there is only one fact table, so no drill-across scenario exists to conform dimensions across.
- **Degenerate dimensions**: `fact.FactSales.LoadRunId` behaves as a degenerate dimension today — a batch/run identifier carried directly on the fact row (sourced from `stg.BatchId`), with no live join to the `ctl.LoadRun` table its name implies (Finding F5).
- **Correctly-implemented edge** (positive note): the `CustomerKey` join is the one relationship in this warehouse that already handles dimension versioning correctly — `usp_LoadFactSales` filters `IsCurrent = 1` before pinning the surrogate key, anticipating `DimCustomer`'s SCD2 design even though the update/versioning half of that design (Finding F2) is not yet built.

## 7. Querying this warehouse

Rules for reading this warehouse, not loading it. They address the ways a report goes wrong
quietly — producing a number, not an error.

1. **Start at `fact.FactSales` and state its grain** — one row per source sales order — before writing any SQL. If a change adds a second row per order (e.g. a per-line-item breakdown), this map is stale; re-run `/map-warehouse`.
2. **Reach an attribute by following a fact key to the dimension that owns it.** Never read `RegionName`, `CategoryName`, or `SegmentName` directly off `fact.FactSales` — those columns are declared but never populated (edge list, row 5); they will silently return `NULL`, not an error. Get region via `DimCustomer.RegionKey → DimRegion`, category via `DimProduct`, and segment via `DimCustomer` directly.
3. **Use `rpt.vwFinanceExtract`'s join path as the usage lead for region**, since it is the only evidenced consumer that reaches `dim.DimRegion`. It shows the path this warehouse uses, not that the result is meaningful yet — `DimRegion` currently holds only a placeholder row (`RegionKey = -1`, `'Unknown'`), so any region-grouped report will show a single "Unknown" bucket until the real region feed lands.
4. **Do not join `fact.FactSales.LoadRunId` to `ctl.LoadRun`** expecting a match — the column's name is misleading (Finding F5); its actual value is `stg.StgSalesOrder.BatchId`. `ctl.LoadRun` is not populated by any load in this repo today.
5. **`CustomerKey` is pinned at load — do not add an `IsCurrent`/`EffectiveFrom`/`EffectiveTo` filter when joining `fact.FactSales` to `dim.DimCustomer`.** The load already selected the applicable version (`AND c.IsCurrent = 1`) and stamped that version's surrogate key onto the fact; re-filtering by `IsCurrent` on the join **would currently return every row** since every customer today has exactly one (never-versioned) row — but once F2 is fixed and real version history exists, re-filtering by `IsCurrent` at query time would silently drop every fact pointing at a superseded customer version. Join on `CustomerKey` alone.
6. **If you need a customer's full attribute history** once F2 is implemented, join on the durable key `CustomerId` across all `DimCustomer` rows for that customer — the version is then **deferred to query**, and you must apply your own `EffectiveFrom`/`EffectiveTo`/`IsCurrent` predicate depending on which point in time you want.
7. **Fan-trap caution**: no bridge/many-to-many table exists in this warehouse today, so joining `dim.DimCustomer` or `dim.DimProduct` directly below the fact is currently safe (each dimension key matches at most one row). Re-check this rule if a bridge table is ever introduced.
8. **Chasm-trap caution**: there is currently only one fact table, so chasm traps (two facts sharing a dimension) do not yet apply — re-check this rule if a second fact table is added.

If a future edge in this map is marked `UNRESOLVED` or `CONFLICTING`, that is the map telling you it
does not know — treat it as a question to ask, not a gap to fill with the most plausible-looking
column.
