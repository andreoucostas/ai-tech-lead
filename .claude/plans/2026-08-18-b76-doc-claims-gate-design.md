# B-76 — `doc-claims`: gate that a shipped doc's description of a command matches that command

**Status:** DESIGN, awaiting adversarial critique (Maintenance model #1). Not authorised for
implementation until the critique is returned, each finding verified, and the design re-locked.
**Filed against:** v0.42.0 · **Re-validated against:** v0.58.0, 2026-08-18 (see Premise below).

---

## 1. Problem — observed, not hypothetical

Three false claims were shipping simultaneously at v0.41.0, each asserting a command performs
maintenance it does not perform:

1. `FRAMEWORK-CONTEXT.md` and all three `README.md`s: *"'Detected Framework Packages' and 'Known
   Hazard Areas' are also refreshed by `/docs-sync`"*. `grep -i hazard` over `docs-sync.md`
   returned **nothing**. The packages half was true, which is what let the sentence survive reading.
2. `rebootstrap.md`'s own frontmatter `description`: *"refresh conventions, **hazards**, and mined
   skills"*. `grep -i hazard` over its body returned **only that line**. Highest-salience of the
   three: the description drives model routing and is what the developer sees in the command picker.
3. `.github/prompts/docs-sync.prompt.md` enumerated the docs-sync workflow as four steps, omitting
   Step 4 and half of Step 2 — and it is a `src/core` file, so it ships to all three dists as the
   only workflow summary Copilot gets.

The first two survived from introduction to v0.41.0. `no-dead-instruction` (check 7) matches script
*invocations* and asserts the file resolves; `DocTruth` covers authoring-repo facts (paths, version
stamps). **Neither has any notion of "this prose describes that command."**

## 2. Premise re-validation (B-83 — this entry is 16 minor versions old)

Checked against the current tree before designing. All three shapes are still ungated:
`$ValidChecks` in `scripts/validate-dist.ps1:48` holds twelve names and none of them is about
claim/command agreement. The three original defects have been *individually corrected* but nothing
keeps them correct — which is precisely the gate's job. What has changed since filing, and what it
changes about the design, is recorded per shape in §4.

## 3. Proportionality (Maintenance model #6 — stated before the design locks)

The harm is **already observed and shipped**, not hypothetical: three simultaneous false claims,
surviving many releases, in the product's highest-salience routing surface. That is a materially
stronger case than B-142's (hypothetical) and comparable to B-58's.

Is a smaller fix available? The obvious one — grep for the exact string `refreshed by /docs-sync` —
is what was already done when the three defects were corrected, and it is why this entry exists:
B-76 records explicitly that *"a check aimed only at the first would have caught one of three."*
The three shapes are three different grammars, and the cheapest instrument that covers the observed
harm is one check with three narrow extractors. Anything narrower re-creates the gap; anything
broader (general prose-claim verification) is NLP, which `DocTruth`'s own header already rejects as
a gate. **Locked at three narrow extractors in one check.**

## 4. Design — `validate-dist` check 13, name `doc-claims`

One new check in **both twins** (`scripts/validate-dist.ps1`, `scripts/validate-dist.sh`), following
check 12 (`step-references`, `validate-dist.ps1:717-782`) as the structural template.

### Shape A — third-party attribution

*Claim form:* `<SUBJECT> … <verb> by /<cmd>` — a doc asserting another command maintains something.

Surveyed in `dist/dotnet`: 58 raw `by /command` mentions. **Most are provenance markers**
(`<!-- Auto-populated by /bootstrap -->`, `<!-- GENERATED by /generate-copilot -->`) which assert
origin, not ongoing maintenance, and carry no subject to test. The checkable subset is a claim whose
subject is **quoted or backticked**.

*Rule:* for each line matching `by\s+`?/(?<cmd>[a-z][a-z-]*)`?`, take the **nearest preceding**
`"…"` or `` `…` `` token on that line as the subject. Resolve `<cmd>` to
`.claude/commands/<cmd>.md` in the same dist. Fail if that file exists and does **not** contain the
subject (case-insensitive, whitespace-normalised). Skip — and **count as skipped** — when the line
has no quoted/backticked subject before the attribution.

*Live instances covered, all currently TRUE* (so the check is green on an unmodified tree and
catches regression, which is the useful direction):

| claim | resolves to | today |
|---|---|---|
| `"Detected Framework Packages" … refreshed by /docs-sync` | `docs-sync.md:48` | ✅ |
| `"Known Hazard Areas" is re-confirmed by /rebootstrap` | `rebootstrap.md:128` (`### 3c: Re-confirm Known Hazard Areas`) | ✅ |
| `` `SECURITY_FINDINGS.md` … Managed by `/security-review` `` | `security-review.md` | ✅ |

*Deliberately out of scope:* an unresolvable `<cmd>` (that is check 7's job, and duplicating it
would produce two findings for one defect).

### Shape B — frontmatter self-description

*Claim form:* a file's own `description:` promising something its body never mentions.

*Corpus:* 12 `.claude/commands/*.md` + 7 `.claude/agents/*.md` use single-line quoted scalars; the
12 `.claude/skills/*/SKILL.md` use `description: >` **block scalars** and must be parsed as such,
not skipped — skipping them silently is exactly the inert-check class (B-59/B-75).

*Rule:* tokenise the description; drop stopwords, the file's own command/skill name, and tokens
shorter than 4 characters; stem-tolerant match (prefix match on the first 5 characters is
sufficient and is what makes `hazards`→`Hazard` work) against the file's body. Fail on any content
token absent from the body.

**This shape carries real false-positive risk, and B-48's lesson is that a false-positive block
costs more trust than the gap it closes.** Therefore the implementation is **two-phase and the
first phase enforces nothing**: run the candidate rule over all three dists, print every finding,
and hand the raw output back for a judgement call on the stopword list and the match threshold.
Only then is the rule enforced. Calibrating against real output is not optional here — guessing the
stopword list and shipping it is how a gate that blocks legitimate work gets built.

### Shape C — step enumeration

*Original rule:* "where a doc lists another doc's steps, assert count and order match."

**This shape's subject has changed since filing, and the design must follow it.** The defect was
fixed by *removing* the enumeration rather than correcting it: all 14 `.github/prompts/*.prompt.md`
now contain **zero** `^N. ` ordered-list lines, so a count-and-order comparison has nothing to
compare. What replaced it is a **prose count claim** — `docs-sync.prompt.md:8` now says *"Follow it
exactly — all six steps: … → … → … → … → … → …"* about `.claude/commands/docs-sync.md`, which has
six step headings. That is one live cross-file instance and it is checkable.

*Rule:* a doc containing a `(one|two|…|ten|\d+)\s+steps` claim **and** naming another shipped
`.claude/commands/*.md` path must have that number equal the named file's top-level step count
(top-level `^\d+\. ` run length, or `^#{1,6}\s+(Step\s+)?\d+` headings — reuse check 12's label
logic rather than writing a second parser).

*Out of scope:* in-file count claims (`rebootstrap.md`'s "three passes", the skills' "Three
checks") — they refer to the containing document and are a different, weaker class.

### Cross-cutting requirements (non-negotiable — these are what stop the check being inert)

1. **Vacuity guards, per shape.** Separate `Fail`s for "scanned zero files", "extracted zero
   claims of shape X", "the extractor is blind". Check 12 (`validate-dist.ps1:772-775`) is the
   pattern. A gate that agrees about nothing is indistinguishable from a gate that agrees.
2. **`-Force` on every enumeration.** PowerShell treats a leading dot as hidden on Linux only, so
   without it the scan silently skips `.claude/` and `.github/` on the CI linux leg while printing
   a clean pass (`validate-dist.ps1:171-177` documents the exact incident).
3. **Blank fenced code before scanning**, and read each Markdown file exactly once.
4. **Register `doc-claims` in `$ValidChecks`** (line 48) and gate on `Test-CheckSelected`; emit
   exactly one `OK`/`Fail` so `Record-Timing` attributes its cost. Add it to the `--content-only`
   set — it is a content check.
5. **Both twins must agree**, and the `.sh` twin must not use bash-4 constructs (`mapfile`,
   `declare -A`) — no shipped script has ever used one, and `scripts/` runs on the CI linux leg.
6. **`grep` exit code 2 must not be treated as "no match"** in the bash twin (B-59's fail-open
   class). Do not write `grep -Eq … && found=1`.
7. Update the twelve-check header comment at the top of both twins to thirteen.

## 5. Tests

Extend `.claude/hooks/tests/ValidateDist.Tests.ps1`, reusing its existing `New-DistCopy` +
`Invoke-Validator -Check doc-claims` machinery (do not add a new harness).

- one green anchor (unmodified dist passes `doc-claims`), both twins;
- **one planted-defect red test per shape**, both twins:
  - **A:** delete the `Detected Framework Packages` line from the scratch copy's `docs-sync.md` —
    this is the historical defect itself, reconstructed;
  - **B:** add a word to a command's `description:` that appears nowhere in its body;
  - **C:** change `all six steps` to `all four steps` in `docs-sync.prompt.md` — the historical
    defect, reconstructed;
- one vacuity red test: point the scan at an empty tree and assert it FAILs rather than passing.

Every red test must be **observed to fail on the unfixed tree** (Maintenance model #4), and the
mutation must be shown to have actually applied — B-84 records two red-tests whose `perl -pi`
pattern never matched, printing a normal green summary that read exactly like an inert check.

## 6. Verification

`build.ps1` ×3 → `git status --porcelain dist/` empty → `validate-dist.{ps1,sh}` ×3 exit 0 →
`ValidateDist.Tests.ps1` → meta suite → BOM sweep + machine-path sweep → both CI legs green.

Scope: `scripts/` and `.claude/` only ⇒ **meta-only, no version bump** under invariant #7 — *unless*
the new check finds a live false claim in `src/`, in which case the correction is a shipped change
and takes the normal release path.
