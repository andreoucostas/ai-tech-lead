# Adversarial critique — B-46 update honesty and B-65 defaults pointer

## VERDICT per item

**B-46 — REJECT this design; retain the item with a materially smaller policy.** The observed harm is real, but the proposed comparison cannot establish what its output claims. A target/incoming difference means either a consumer edit **or an ordinary framework version change**, and this installer also has transforms, merges, exclusions, generated mirrors, and ownership exceptions. The resulting list would be noisy by construction and would train consumers to ignore it. Ship an unconditional, precise preflight/closing disclosure instead: update replaces framework-owned files; commit or copy local changes first; `.claude/settings.json` is included; review the resulting diff. Add a single rolling pre-update backup of `.claude/settings.json` so the uniquely team-edited configuration remains recoverable without git. Do not skip it wholesale, because new or corrected framework hook registrations must still arrive. Defer any claim to identify *locally modified* files until there is a trustworthy old-version baseline or ownership-aware three-way model.

**B-65 — DROP the durable pointer; complete only the documentation correction.** The measured premise is now that agents can discover `docs/defaults.md` without a pointer, while benefit from restoring one is unmeasured. A line in protected `CLAUDE.md` is not cheap insurance for the installed population: update restores the old file, so the line reaches new installs only. Putting the pointer in the unprotected framework-rules carrier would reach updates, but would spend always-on context for an unmeasured reliability gain. Keep `docs/defaults.md` as bootstrap input/on-demand guidance and add the missing on-demand-docs tier to `docs/enforcement-surfaces.md`; do not claim a routing improvement.

## BLOCKING

1. **The comparison does not distinguish consumer edits from framework upgrades.** Evidence: §3 compares the current target with “the file the installer is about to write.” On a normal update, every file changed between the installed framework version and the incoming version differs even when the consumer never touched it. Why it matters: the heading “had local modifications” would be false, and a release with many changed files would generate the most noise. Specific change: remove the per-file local-modification detector from B-46. If exact attribution is ever required, specify a three-way baseline (old shipped content, target content, new shipped content) and how old content is obtained; otherwise use unconditional ownership disclosure.

2. **The proposed compare set is not the installer’s effective write set.** Evidence: both installers bulk-copy most top-level entries, separately copy `docs/`, preserve an existing `docs/wiki/INDEX.md`, exclude template metadata plus `LICENSES/` and `NOTICE-ai-tech-lead.md`, then apply the legal-file policy, delete the shipped installer twins and `template-ci.yml`, restore protected files, merge skill state, regenerate `.github/skills`, and possibly rewrite `.claude/settings.json` for the available interpreter. Why it matters: comparing the dist tree before the write produces both false positives and reports for files whose final installed content is not the source content. Specific change: do not implement the generic pre-copy walk. Any future detector must compare final effective output and explicitly classify every exceptional path.

3. **Legitimate per-install content guarantees false positives.** Evidence: update restores `origin: discovered` skills, appends a consumer exemplar line to refreshed framework skills, keeps disabled skills inactive, and rebuilds `.github/skills` from the resulting `.claude/skills`. Bash rewrites `settings.json` from `pwsh` commands to bash when `pwsh` is unavailable; PowerShell has the corresponding host-dependent settings handling. Why it matters: these files are supposed to differ from their dist copies. A warning on correct preservation/host adaptation destroys the warning’s credibility. Specific change: exclude these from any source comparison; tests must cover discovered skills, exemplar-bearing skills, disabled skills, generated `.github/skills`, and both settings interpreter outcomes.

4. **The `CLAUDE.md` pointer cannot reach existing consumers.** Evidence: `CLAUDE.md` is in `$protected`; update snapshots and restores it after the bulk copy. B-97 records this exact delivery wall. Why it matters: §4 proposes a carrier that misses the population whose post-bootstrap discovery it is meant to improve. Specific change: delete the `CLAUDE.md` option from the design. If a pointer is retained despite the weak proportionality case, use the unprotected framework-rules carrier and state its always-on context cost; my recommendation is to drop the pointer.

5. **The DoD’s red test would validate a false instrument.** Evidence: “plant a modification, confirm it is named” proves only that unequal files are named; “clean update names nothing” can pass only when old and new framework payloads are identical. The constructible success state for a real update containing changed framework files is absent under this algorithm. Why it matters: Maintenance rule 4 requires both a red observation and a reachable success state; this test cannot prove local-edit attribution. Specific change: replace it with output-contract tests for the unconditional warning and settings backup. If a detector is redesigned with an old baseline, test four distinct cases: unchanged old file, consumer-only edit, framework-only change, and both changed.

## NON-BLOCKING

6. **`settings.json` deserves different treatment, but not skip-with-warning.** Evidence: it is shipped, deliberately committed team configuration (v0.38.1), contains permissions and hook registrations, is demonstrably edited, and is host-transformed after installation. A hook or skill is primarily framework machinery; settings is a mixed-ownership integration point. Why it matters: overwriting it can discard team policy, while skipping it can silently withhold security/build/audit hook registrations—the same stale-delivery class the design invokes against skipping. Specific change: before overwrite, save the existing file to one documented rolling backup path, then install and host-adapt the current settings and name both paths in output. File a later structured-merge/ownership design only if observed recovery pain justifies it.

7. **A named list is not reliably actionable for dirty or non-git consumers.** Evidence: the proposed remediation says “recover from git history,” but the installer neither requires a clean tree nor even requires git. A dirty worktree also makes the post-update diff ambiguous: the overwritten content is gone from the working tree and may never have been committed. Why it matters: detection after destruction is notification, not recovery. Specific change: preflight output must say to commit/stash/copy edits before continuing; the settings backup supplies recovery for the sharpest observed case. Do not promise git recovery.

8. **Skip-with-warning was rejected too broadly, but the settings-only middle is still unsafe.** Evidence: the design equates every skip with B-97, yet ownership differs by path; nevertheless settings carries framework hook registrations that must evolve. Why it matters: the policy analysis needs to distinguish pure consumer ownership, pure framework ownership, and mixed ownership instead of treating all files alike. Specific change: record the three classes explicitly. Continue restoring the eight protected paths, overwrite framework machinery with honest warning, and backup-then-refresh mixed `settings.json`.

9. **Legal paths require explicit policy tests, not inclusion in the warning walk.** Evidence: an identical `LICENSES/ai-tech-lead-MIT.txt` is retained, a differing collision is refused before mutation, and `NOTICE-ai-tech-lead.md` is overwritten only when its existing copy is marked `FRAMEWORK-OWNED`; both are excluded from bulk copy. Why it matters: reporting either as a clobbered local modification would contradict the installer’s existing refusal/ownership contract. Specific change: state that B-46 does not alter legal-file policy and add regression assertions that its messages and exit behavior remain unchanged.

10. **The wiki path and deleted meta artifacts need explicit exclusions.** Evidence: `docs/wiki/INDEX.md` is copy-if-absent; `scripts/install.{ps1,sh}` and `.github/workflows/template-ci.yml` are removed after bulk copy; root template metadata is never copied. Why it matters: “each file the installer is about to write” is underspecified at precisely the paths where write intent differs from final state. Specific change: enumerate these in the installer ownership registry/tests even under the recommended no-detector policy.

11. **The design omits consumer documentation and decision registries that enumerate update behavior.** Evidence: root `README.md` and all three shipped stack READMEs describe update as refreshing framework machinery while leaving consumer-owned content untouched; installer header comments repeat it. `meta/workspace-decisions.md` contains the update/ownership decisions, including the mixed ownership problem around skills and protected delivery. Why it matters: changing only runtime text leaves the documented contract stale and loses the policy rationale. Specific change: update root README, all three source stack READMEs (including the monorepo sibling), both installer headers, and record the ownership/disclosure decision in `meta/workspace-decisions.md`; include all in the DoD and changelogs.

12. **The DoD does not cover message ordering or failure semantics.** Evidence: legal collision checks occur before mutation, while the proposed warning is described after the copy; prior update defects copied files and then aborted before the completion banner. Why it matters: a consumer needs the ownership warning before destructive writes, and a partial failure must not print success. Specific change: assert preflight disclosure precedes the first mutation, completion text appears only on exit 0, and refusal/partial-failure paths do not claim a completed update.

13. **B-65’s documentation row needs an honest tier definition.** Evidence: `enforcement-surfaces.md` currently defines only Guaranteed and Instructed, but `docs/defaults.md` is neither automatically loaded nor unreachable; the backlog measurement observed unaided discovery once. Why it matters: calling it Instructed would overclaim delivery, while calling it unreachable repeats the superseded premise. Specific change: add an “On-demand/discoverable” definition and row stating that loading is task/model dependent and not guaranteed, with `docs/defaults.md` as the example.

14. **Per-item proportionality points in opposite directions.** Evidence: B-46 has an observed destructive outcome across four classes, but the compare pass is both more costly and less truthful than a precise warning; B-65 has one successful no-pointer discovery and no measured pointer effect. Why it matters: rule 6 asks whether a smaller fix removes most observed harm. Specific change: for B-46 ship disclosure plus one rolling settings backup and drop the detector; for B-65 explicitly DROP the pointer and retain only the missing-tier documentation correction.

## CHECKED AND FOUND CORRECT

15. **Overwriting framework-owned machinery is necessary to deliver fixes.** The design is right not to propose preserving every modified skill, hook, or script. The existing discovered-skill, exemplar, disabled-skill, and protected-file exceptions already encode narrower consumer ownership.

16. **LF-normalized comparison is appropriate where semantic file equality is actually needed.** The legal-license policy already uses this shape in both twins. It does not solve the missing old-version baseline, but line endings alone should not create a conflict.

17. **Archive-everything and a general three-way merge are disproportionate for the evidence currently recorded.** They add state/lifecycle or complex merge semantics without a demonstrated need beyond honest loss prevention. A rolling backup for the one mixed-ownership file is the narrower exception.

18. **The misleading completion language must change in both twins.** Naming the protected paths is more honest than the current broad phrase, but it must be paired with an explicit statement that framework-owned files—including settings—are replaced.

19. **`UpdateDelivery.Tests.ps1` is the correct behavioral suite to own the update contract.** It already executes both twins, asserts protected/unprotected behavior, skill preservation/merge behavior, and all-dist completion. Extending it is correct; the missing piece is a truthful output/backup contract rather than the proposed equality detector.

20. **Adding the missing on-demand documentation tier is worthwhile independently of the pointer.** It corrects the framework’s enforcement model without claiming that a pointer changes model behavior.
