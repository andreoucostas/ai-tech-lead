# Adversarial critique — B-58 / B-60 / B-82

VERDICT: **B-58 — PROCEED WITH CHANGES (Part A only; DROP Part B). B-60 — PROCEED WITH CHANGES (the locked grammar is not implementable as written). B-82 — DROP / REJECT.**

## BLOCKING findings

### 1. A3 is factually wrong and “green under exactly these rules” is not reproducible

**Evidence.** The design says a zero start is required in “5 shipped files” and that all dists are green under “exactly these rules” (`.claude/plans/2026-08-16-b58-b60-b82-mirror-drift-gates.md:130-146`). I enumerated the stated scope with `Get-ChildItem` and extracted `^0\. ` labels. Real output was:

```text
dotnet files=33 refsFiles=15 zeroFiles=6
 ZERO dist\dotnet\.claude\skills\add-endpoint\SKILL.md,
 dist\dotnet\.claude\skills\add-entity\SKILL.md,
 dist\dotnet\.claude\skills\add-warehouse-load\SKILL.md,
 dist\dotnet\.claude\skills\map-warehouse\SKILL.md,
 dist\dotnet\.claude\skills\register-service\SKILL.md,
 dist\dotnet\.claude\commands\bootstrap.md
angular files=31 refsFiles=11 zeroFiles=5
monorepo files=37 refsFiles=15 zeroFiles=10
```

The allowance is required, but the asserted count is false for dotnet and monorepo. More importantly, §2.2 says a block is broken by a column-zero nonblank line, yet does not define whether headings, tables, blockquotes, HTML, thematic breaks, fenced code, or a top-level continuation paragraph end the semantic procedure. It excludes fences only from *reference extraction*, not list-label extraction. Thus no unique instrument exists whose current green can be re-derived.

**Why it matters.** Maintenance rule 3 forbids recording this as an observation, and the user explicitly makes a wrong A measurement blocking. Implementers can produce materially different parsers that all claim conformance.

**Recommendation.** Replace §2.2 with a line-state grammar and fixtures before locking it. At minimum define fence handling for both assertions, indentation, list interruption/restart, blockquotes, tables, HTML blocks, and whether a first label other than 0/1 is legal. Re-run and record exact inventories per dist, not “and others” or one cross-dist count.

### 2. B-60’s proposed block rule has both cheap false positives and structural false negatives

**Evidence / concrete false positive.** In `dist/dotnet/.claude/skills/add-tests/SKILL.md`, insert a legitimate table or blockquote between items 2 and 3:

```markdown
2. **Choose the level.** ...

| Signal | Level |
|---|---|
| HTTP boundary | integration |

3. **Create the harness.** ...
```

The stated column-zero rule breaks the block at `| Signal`, making `3.` a new block. If starts are restricted to 0/1 as the design implies, it falsely fails; if every block may start at its own arbitrary label, the check accepts the original `0,2,3...` defect by treating each item after any column-zero continuation as a fresh block. A blockquote has the same problem. An indented continuation does not break, creating formatting-dependent semantics for identical rendered prose. A fenced sample containing column-zero `1.` and `3.` is scanned by contiguity because only reference extraction is told to blank fences. An indented code sample is ignored because it does not match `^\d+`, so the two Markdown code grammars behave differently.

**Evidence / concrete false negative.** A nested ordered procedure under item 2 in that same file:

```markdown
2. **Prepare.**
   1. First nested action.
   3. Third nested action.
3. **Run.**
```

is invisible to `^\d+\. ` despite rendering a broken ordered list. Conversely, a semantically new top-level list after blank lines is merged with the prior block because blanks do not break it. The proposed check therefore neither models Markdown lists nor the narrower “procedure step” concept consistently.

**Why it matters.** This is the central B-60 measurement, not an edge case. The proposed cheap regex is pretending to be a Markdown block parser.

**Recommendation.** Do not implement block grouping as written. Use the materially smaller measure: within files already known to contain a canonical top-level procedure, validate explicitly identified procedure ranges (finite registry of file + start heading), or limit B-60 to unresolved explicit references. If a generic parser is retained, use a real CommonMark parser and justify the dependency/cost.

### 3. B-60 reference extraction confuses declarations, prose, ranges, and semantics

**Evidence.** The real tree contains `### Step N` and `## Step N` declarations, e.g. `dist/dotnet/.claude/commands/feature.md:13-44`, `docs-sync.md:12-58`, `security-review.md:83`, and `skills/perf/SKILL.md:22-152`. A literal `step N` regex counts those declarations as references unless headings are explicitly excluded. My fence-aware literal scan reproduced the plan’s “15 files carrying references” for dotnet, but ten of those were heading-based files, including `perf`; that count therefore does not establish 15 prose-reference files.

Concrete misses in `dist/dotnet/.claude/skills/add-tests/SKILL.md`:

```markdown
Repeat steps 1-3.       # plural/range is not matched by singular `step N`
Use the preceding step. # no number, cannot be resolved
Continue in a later step. # no number, cannot be resolved
```

Concrete false confidence:

```markdown
Apply step 4 above.     # passes if any label 4 exists anywhere, even in an unrelated second list
Apply Step 0.           # passes whenever an unrelated pre-flight 0 exists
```

The design expressly chooses file scope (`§2.2`), so a reference can resolve to the wrong list and still be green. “steps 1-3” is common English that its named “step references” gate silently ignores.

**Why it matters.** The check’s reported coverage can be inflated by declarations, while the claimed defect class remains undetected. That violates the anti-vacuity discipline documented at `meta/LEARNINGS.md:596-600`.

**Recommendation.** Define “reference” separately from “definition”; exclude heading declaration lines; support `steps N-M` or explicitly declare it out of scope and forbid that grammar. Prefer explicit anchors or a finite procedure registry if references must bind to the right list. Add a coverage assertion for *prose references*, not regex hits including headings.

### 4. B-58 Part B is wrong at the consumer vantage point and should not ship

**Evidence.** `template-checks` runs inside consumer repositories through `docs-sync-check`; `src/core/scripts/docs-sync-check.sh:138-141` delegates to it. Consumer `/bootstrap` explicitly tells the agent to audit, add, remove, and adjust skills and then update CLAUDE’s Common Tasks (`dist/dotnet/.claude/commands/bootstrap.md:172`). `/generate-copilot` regenerates AGENTS as a deliberately bounded mirror and includes Common Tasks (`dist/dotnet/.claude/commands/generate-copilot.md:61-79`); bootstrap invokes that regeneration (`dist/dotnet/.claude/commands/bootstrap.md:227-231,307-310`).

Concrete legitimate consumer input:

```markdown
# CLAUDE.md
- `add-tests` — run `dotnet test` with the project harness

# AGENTS.md, legitimately condensed by the generator
- `add-tests` — add tests following project patterns
```

The slug and skill ownership agree; code-span sets do not. The proposed gate fails a consumer immediately after the framework’s own model-driven generator legitimately condenses the prose. A consumer-specific skill such as `reconcile-ledger` with `` `LedgerDbContext` `` in canonical CLAUDE and “reconcile ledger entries” in bounded AGENTS has the same outcome.

Concrete false negative:

```markdown
# CLAUDE
- `add-tests` — use NUnit with `WebApplicationFactory`
# AGENTS
- `add-tests` — use xUnit with `WebApplicationFactory`
```

The code-span sets are equal and the technologies conflict. The live Angular line itself demonstrates the weakness: `Jasmine/Karma or Jest` is plain prose (`dist/angular/AGENTS.md:100`) while only `HttpTestingController` is caught (`dist/angular/CLAUDE.md:72`).

**Why it matters.** A shipped consumer gate that rejects legitimate customisation/regeneration is worse than no gate. The proposed authoring-time heuristic is not a consumer invariant.

**Recommendation.** DROP Part B. Keep Part A slug-set/duplicate parity, because both generated surfaces promise the same skill inventory. Fix the live Angular source drift directly. If technology parity is desired, make it an authoring-only targeted test over the three stock dists, never a shipped consumer check—but its vocabulary/maintenance cost is not proportionate to one live line.

## NON-BLOCKING findings

### 6. Twin parity risks are known and need fixture-level controls, not “same text” alone

**Evidence.** This repo has already been bitten by all the relevant families:

- CRLF content comparison: `meta/LEARNINGS.md:47-55` records a false mirror failure and requires identical EOL normalization.
- Non-ASCII byte handling: `meta/LEARNINGS.md:120-128` records a `sed` bracket expression containing an em dash corrupting UTF-8 and making composer twins disagree.
- Locale/sort: `meta/LEARNINGS.md:283-287` records a post-ship `sort` collation finding.
- Console/codepage: `meta/LEARNINGS.md:289-292` records two failures under ibm850 after UTF-8-host greens.
- PowerShell 5.1 singleton count: `meta/LEARNINGS.md:614-617` records `(pipeline).Count == $null` for exactly one object; the plan correctly calls for `@()`.
- Set comparison: `meta/LEARNINGS.md:619-620` says set comparison hid ordering, duplicates, and omissions. B-58 A therefore needs separate duplicate checks before set equality.

Likely implementation divergences are: PowerShell `-contains`/hashtable key comparison is case-insensitive unless the `-c*` variants/ordinal comparers are chosen, while bash strings are case-sensitive; `Sort-Object` culture ordering differs from `LC_ALL=C sort`; .NET regex supports constructs grep/sed do not and treats Unicode/case differently; `Get-Content` strips CRLF while raw grep/sed may retain `\r`; and literal em dash/arrow characters can be decoded, rendered, or matched differently. Skill lines contain both `—` and arrows now.

**Why it matters.** Equal exit code/message on one ASCII mutant does not establish twin semantics.

**Recommendation.** Specify ordinal, case-sensitive slug comparison; avoid sorting for correctness (sort only diagnostics under an explicitly identical ordinal/C locale); normalize BOM/CRLF before parsing; avoid non-ASCII bracket expressions; run fixtures containing `—`, `→`, CRLF, duplicate singleton/multiple slugs, and case variants under Windows PowerShell 5.1, pwsh 7, and bash. Compare ordered normalized records, not sets.

### 7. B-60’s direct runtime is negligible; its test-process multiplication is the real cost

**Evidence.** I timed 100 read-and-regex passes over the 33 dotnet scoped files:

```text
files=33 iterations=100 elapsed_ms=673 per_dist_pass_ms=6.74
```

`meta/gate-budget.json` records `dist-gates` at 459.4s historically, two later loaded runs at 668.4s/609.4s, and a 700s ceiling. It also says process creation—not file scanning—is the bound. `ValidateDist.Tests.ps1:100-104` records roughly 40s per bash case when it used broad runs, and the budget identifies that suite as the dominant cost.

**Why it matters.** The production pass will add approximately hundredths of a second per dist, well below timing noise. Several new red cases that each spawn both validators can add minutes to the meta suite and push loaded releases toward ceilings.

**Recommendation.** Read each scoped file once during the check and perform all state-machine assertions in memory. In tests, create one scratch dist and batch multiple mutations through a purpose-built fixture/isolated named check, or add direct parser unit fixtures rather than launching a full validator per grammar edge. Measure the added meta-suite time; do not raise the dist-gates ceiling for this scan.

**Why it matters.** This check catches “a heading was added without updating a second hard-coded heading table,” not whether the mirror was updated. The table is a second manually maintained representation and produces ceremony without guarding the observed content loss.

**Recommendation.** DROP B-82. The smaller fix is a DocTruth assertion that the root AGENTS banner explicitly identifies CLAUDE as canonical plus a review checklist/search when root `##` headings change, or simply retain the existing invariant. Revisit only after a real root-mirror omission occurs and then design a measure for the missing concept, not heading topology.
