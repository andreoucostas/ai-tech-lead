## BLOCKING 1 — Delivery is capped by B-97, and the design does not know it

B-136 changes **Agentic Workflow §5–6**. `Agentic Workflow` is one of the four framework-owned
blocks that WSD-031 moved out of `CLAUDE.md` into
`.github/instructions/framework-rules.instructions.md`. That has a consequence the design never
states:

| Consumer | Receives the new completion rule? |
|---|---|
| Copilot (CLI + VS Code) | **Yes** — carrier is read natively, unprotected, delivers on update |
| Claude Code, greenfield or migrated | **Yes** — via the `@import` |
| Claude Code, installed before v0.45.0 and not yet migrated | **No** — holds a stale inline §5–6 that still says *flag* |

Worse than "no": for that third population both texts can be visible at once, and **which one a
model follows is unmeasured** — that is B-97's open successor question, explicitly needing B-98's
six-run rule. So B-136 could ship a completion contract that a real consumer's agent reads in its
*old* form and be indistinguishable from success.

**Required:** (a) state this delivery ceiling in the design; (b) make the shipped changelog entry
name its delivery surface, which is the cheap, independently-shippable consequence B-97's own
changelog sweep already identified — *"the release process must state the delivery surface per
item"*; (c) sequence B-136 **after** B-97's migration-state row, which is the thing that tells an
un-migrated consumer to delete the stale copy. This review does not require B-97's *successor
measurement* to complete first — only that the ordering is deliberate and the ceiling disclosed.

## BLOCKING 2 — The outcome measure is deferred behind a conditional, which is how it becomes unreachable

Step 4 reads: *"Add behavioral fixtures **only if** an existing agent-eval scenario can distinguish
'changed mapped structure but stale map' from 'unrelated SQL change'."* That conditional can resolve
to "no fixture" at implementation time, leaving the item shipped on Markdown substring checks — and
the design's own verification contract already concedes those *"prove instruction delivery, not that
a model follows it."*

Maintenance model #4's second half — added *because* of B-112 — requires naming the concrete,
constructible world in which the measure would register success **before** the work starts, not
discovering at the end that none exists. B-112's finding was that all three behavioural instruments
built in this repo were broken in their first version, in three different directions.

**Required:** resolve the conditional now, in the design, one way or the other. Either name the
fixture and its answer-key-free grader, or state plainly and in the shipped record that **B-136 ships
as an unmeasured prose contract** whose compliance is not evidenced. Both are acceptable outcomes.
Silently taking the second while the design implies the first is not.

## SCOPE REMOVAL — drop step 3 (the warehouse trigger) from this item

The gate asked whether a shared-rule-only change removes most of the harm. **It does, and the
warehouse trigger should come out**, for three reasons the design does not weigh:

1. **Its carrier is measured-weak.** B-98 step 1 (2026-08-06) measured `map-warehouse` at
   **r = 0 of 6** — never invoked, despite being named in always-loaded Common Tasks. And B-126's
   2026-08-15 correction found `add-warehouse-load` actually fired in only **1 of 6** counted trials.
   A post-change duty written *into* a warehouse skill inherits that reach problem. The generic
   completion rule, by contrast, rides the always-loaded rails.
2. **The generic rule may already cover it.** `docs/warehouse-map.md` is already a row in the
   ownership table with a fully specified trigger and action. If the causal rule — *the actor that
   invalidated an artifact owns refreshing it* — is stated well, the warehouse case is an instance,
   not an exception. The design asserts generic wording "cannot encode the trigger" without testing
   the claim.
3. **It is the only part that needs warehouse fixtures**, which is what makes this item M rather
   than S, and it is the part most exposed to blocking 2.

Re-file it as its own entry, gated on evidence that the generic rule failed the warehouse case.
If a later drill or field report shows the generic rule under-triggering there, that is the
evidence — and it will also say what the trigger should be, which nobody currently knows.

## BINDING REFINEMENT 1 — the ownership table must not ship as an inventory

The design flags this risk itself (*"without becoming a second, stale inventory of framework
files"*) and proposes the fix, then leaves it optional. **Make it binding:** durable *principles*
go in the shared workflow; file-specific triggers stay in the artifacts and skills that already own
them. A shipped table listing eight artifact classes is a maintenance liability that goes stale
silently — this repo's own history has the 41%-wrong backlog index as the precedent for what an
unmaintained inventory does.

## BINDING REFINEMENT 2 — keep the protected-records carve-outs as the primary rule, not a caveat

The strongest part of this design is its ownership semantics: append-only `LEARNINGS.md`, registers
with their own evidence/authority contracts, human-intent ADRs, generated mirrors regenerated rather
than hand-edited. The failure mode of "reconcile affected artifacts" is an agent that
*helpfully* rewrites a security register or fabricates an ADR rationale to make the repo
self-consistent — strictly worse than the stale state it replaces, and harder to detect. Codex's
first-round review caught exactly this. Keep those carve-outs load-bearing and prominent in the
shipped wording, not appended as exceptions.

## Points examined and found sound

- **Causal ownership model** — correct, and the SQL example (changing a mapped key triggers; an
  unrelated SQL edit does not) is the right discrimination. Keep the false-positive control.
- **Update-vs-flag boundary** — the three-outcome close (`updated` / `Affected artifacts: none` /
  named blocker) is well formed; it forbids the silent fourth outcome, which is the actual defect.
- **`/docs-sync` stays read-mostly** — correct. Converting it to an auto-writer was rightly rejected.

## Proportionality — my own assessment

The observed harm is **textual, not behavioural**: the baseline observes that the contract *permits*
finishing after flagging drift. No incident is cited where an agent left a stale artifact and it
cost something. That is still a legitimate defect and the maintainer has asked for it — but it caps
the machinery justified, which is the second reason to drop step 3. With steps 1–2 only, this is an
**S** item that changes normative wording on the always-loaded rails and is delivered by the existing
composer, with no new fixtures, no new inventory, and no warehouse dependency.

## Disposition

**Locked for implementation once blocking 1 and 2 are written into the design, step 3 is removed and
re-filed, and both refinements are marked binding.** Record in `meta/workspace-decisions.md`, per the
gate. Implementation may then proceed; the implementer must be a different session from this review.
