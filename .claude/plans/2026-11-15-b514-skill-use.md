## Question and hypothesis

B-346 observed `/bootstrap` drafting skills; the late-fee follow-up (B-331) saw none of 4 follow-up tasks call the drafted skill. A draft
is not in `AGENTS.md > Common Tasks` until approved, and that list is what tells the agent to invoke a skill. Questions: (1) is the skill
called with the Skill tool on the next task that matches it, as a draft and once approved; (2) is every non-obvious step of the operation
present in the result, with and without the skill.

Predictions, written before any run: the approved skill is called in at least 4 of 6 runs and the draft in at most 1 of 6; every arm
completes the operation in at least 5 of 6 runs, because the fixture holds three instances of each operation to copy (B-331's arm with no
`/bootstrap` landed the same, 3 of 3).

## Grading (`assertion: skillUse`, arm-neutral; files and transcript, never the final message)

Per run, from the target's working tree against the overlay commit (or the fixture commit, bare), and from the stream:
- **skill**: a Skill tool call, main agent or sub-agent, whose `skill` is the operation's drafted slug (from the overlay: the
  `origin: discovered` draft whose text names `EventRegistry` for P1 and `ReportCatalog` for P2). Reported beside it: every Skill call's
  name, a Read of that draft's `SKILL.md` without a Skill call, and the number of denied tool calls.
- **complete**: every non-obvious step present, a step being one whose omission neither the build nor the existing tests catch. P1, for
  the new `IIntegrationEvent` type (not one of the three it ships): `registry`, an uncommented `Register<NewEvent, Handler>("…", "…")` in
  `EventRegistry`; `version`, the type's `[EventVersion(N)]` and a `contracts/events/*.vN.schema.json` with the same N that the run
  wrote, the one the registry line's schema path names when the line exists; `di`, an uncommented `Add{Scoped,Transient,Singleton}<Handler>` or
  `(typeof(Handler))` registration of the concrete handler, which `OutboxDispatcher` resolves with `GetRequiredService`. P2, for the new
  `IReportExport` class: `catalog`, an uncommented `new <Class>(` in `ReportCatalog`; `flag`, `"reports.export.<its Key>": true` in
  `config/feature-flags.json`; `grant`, an uncommented `GRANT SELECT ON <its ViewName> TO ReportReader` in a `.sql` file under `db/`
  (brackets ignored; whether it is in `db/security/reporting-grants.sql` is reported). The entry's four (registry, version, flag, GRANT)
  are each reported.
- Secondary, reported only: P1 the `EventRegistryTests` row and a `new NewEvent(` raise; P2 the view file, the `ReportCatalogTests` row
  and the export's `Key`; cost (`total_cost_usd`), duration, `system/init` model. After round 3, `dotnet build Orders.sln` in each
  retained target, recorded by hand.
- The grader decides. Every Skill-call value and every not-complete row is hand-checked against the stream and the files; a disagreement
  is reported beside the grader's value, never silently replaced. The grader is shown red before any run (self-test, known-bad outputs).

## Readings and decision rule (k of 6 valid runs per arm; a difference of 1 is noise at this n)

- Use: DRAFT-USED if draft `skill` is at least 3 of 6, DRAFT-UNUSED if at most 1; APPROVED-USED if approved `skill` is at least 4 of 6,
  APPROVED-UNUSED if at most 1; otherwise SOMETIMES.
- Outcome: SKILL-CHANGES-OUTCOME if approved or draft `complete` exceeds no-skill by 2 or more and the runs that called the skill
  completed more often than those that did not; NO-DIFFERENCE if approved and draft are each within 1 of no-skill; CEILING if no-skill
  and bare are each at least 5 of 6; CONVENTIONS-HELP if no-skill exceeds bare by 2 or more.
- B-516 (one-action approval): APPROVED-USED with DRAFT-UNUSED: approval is what makes a draft work, so the one action is worth building,
  and an unreviewed draft being followed was not observed on Claude Code. DRAFT-USED: an unreviewed draft is followed, so where an
  unchecked draft sits comes first, after B-515's check. APPROVED-UNUSED: approval does not produce use; B-516 waits, and a trigger
  candidate (description or Common Tasks wording) is measured first.
- B-515 (check a draft against its instances): SKILL-CHANGES-OUTCOME, or any run that called the skill and then missed a step it
  states: a draft's missing step reaches the result, so B-515 proceeds. NO-DIFFERENCE at CEILING: this fixture cannot show a step check's
  value, because the code alone shows every step; B-515's before-and-after needs a fixture whose instances hide a step. NO-DIFFERENCE below
  CEILING: a used skill does not fix missed steps; B-515 drops in priority.
- B-356 (offer a test, Conventions line or draft): SKILL-CHANGES-OUTCOME with APPROVED-USED: a draft earns its place and B-356 proceeds as
  designed. CONVENTIONS-HELP with NO-DIFFERENCE: a Conventions line carries the value at less cost, so B-356's offer should prefer it.
  NO-DIFFERENCE, CEILING and no CONVENTIONS-HELP: no measured value on this shape; B-356's decoy false-offer rate decides alone.
- Records: B-514's Claude Code design is answered when every arm has 6 valid runs. The entry names a Copilot leg this run does not do, so
  the entry is then narrowed to that leg rather than deleted, and the commit says "measured"; fewer valid runs also leave it open, with the
  partial counts. B-515, B-516 and B-356 each get the reading that applies, one line in their status; a proposed fix is one line, not made.
- Not shown: Copilot CLI and VS Code; other models; other operation shapes; drafts of other quality (one generation is used throughout);
  a real consumer repository; interactive use (headless `-p`, approval clause in the prompt).
